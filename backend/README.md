# Member 2 – Backend Developer

## Your responsibilities (from the project proposal)
- FastAPI/Flask application
- APIs
- Database
- Frontend–backend integration

## What's in this package

| File | Purpose |
|---|---|
| `app.py` | FastAPI app with all API routes: `/api/chat`, `/api/schemes/search`, `/api/eligibility/check`, `/api/health`. CORS enabled so the frontend can call it from a different origin/port. |
| `database.py` | SQLite setup: `chat_sessions` (tracks each conversation's accumulated user profile) and `chat_messages` (full message history, used to give the LLM conversational context). |
| `models.py` | Pydantic request/response schemas — this is the API contract Member 1 (Frontend) builds against. |
| `requirements.txt` | Backend-only dependencies. |

## Setup

```bash
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

This backend imports from the `rag_pipeline/` (Member 3) and `llm_nlp/` (Member 4) packages at runtime, so for local development place all four member folders as siblings inside one project root, e.g.:

```
project-root/
├── backend/       <- this package
├── frontend/
├── rag_pipeline/
└── llm_nlp/
```

You'll also need Member 3's and Member 4's `requirements.txt` installed in the same environment, and `ANTHROPIC_API_KEY` set (see `llm_nlp/README.md`).

## Run the server

```bash
cd backend
uvicorn app:app --reload --port 8000
```

Visit `http://localhost:8000/docs` for interactive Swagger API docs (auto-generated by FastAPI) — share this link with Member 1 for frontend integration.

## API summary (contract with Member 1 – Frontend)

### `POST /api/chat`
```json
// request
{ "session_id": "optional-existing-id", "message": "I am a farmer in Andhra Pradesh" }

// response
{
  "session_id": "uuid",
  "reply": "...",
  "language": "en",
  "profile": { "age": 62, "state": "Andhra Pradesh", "occupation": "farmer" },
  "matched_schemes": [ { "scheme_id": "...", "scheme_name": "...", "match_signal": "likely_match", "reasons": [...] } ]
}
```
Omit `session_id` on the first call to start a new conversation; reuse the returned `session_id` on every follow-up so profile + history accumulate.

### `POST /api/schemes/search`
Direct semantic search over the scheme knowledge base (for a search-bar UI, outside the chat flow).

### `POST /api/eligibility/check`
Check one specific scheme against a profile (for an "Am I eligible?" button on a scheme card).

## Notes for review / demo

- SQLite is used for simplicity in the demo/hackathon stage. For production, swap the connection logic in `database.py` for Postgres — the SQL is plain enough that this should be a small change.
- `_rag_pipeline` (the vector index) is loaded once at server startup (`@app.on_event("startup")`), not per-request, since embedding model + FAISS index loading is relatively slow.
- CORS is currently wide open (`allow_origins=["*"]`) for ease of local development — restrict this to the deployed frontend's actual origin before going live.
- Error handling on `/api/chat` currently returns a generic 500 with the exception message; consider more specific error codes (e.g. rate limiting, invalid session) as the project matures.
